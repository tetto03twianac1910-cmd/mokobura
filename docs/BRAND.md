# もこブラ ブランド基礎文書（BRAND.md）

このドキュメントは、もこブラのブランドの「基礎」を記録し、今後の改善で育て続けるための生きた文書です。
デザインは一回の作り替えで完成するものではなく、週次の改善を積み重ねながらブランドとして構築していくもの——という方針（2026-11-21 トーイ指示）に基づき、判断に迷ったらここへ立ち返り、決めたことはここへ追記します。

最終更新: 2026-11-21（第一歩：公式サイトの編集デザイン化）

---

## 1. コンセプト

**毎日開くブラウザを、好きな世界に着せ替える。静かな絵と、編集の美しさで。**

- 実用品（ブラウザ）に「着せ替え」という楽しさを足す、という Simeji 的発想が核。
- 可愛さは「甘さ」ではなく「静けさと品」で表現する。世界観の統一感こそがブランド。
- 第一印象で「可愛い、使いたい」と思わせること。説明より先に絵と佇まいで伝える。

## 2. タイポグラフィ規則

| 用途 | フォント | 備考 |
|---|---|---|
| 見出し | Shippori Mincho（しっぽり明朝） | ウェイト 500–700。`font-feature-settings: "palt" 1` で約物を詰める。字間 0.04–0.06em、行間 1.55–1.6 |
| 本文 | Zen Kaku Gothic New | ウェイト 400 中心、強調 500。行間 1.9–2.1、字間 0.03em。1行は最大でも 40 字前後を目安に幅を絞る |
| 英字ラベル | Jost（細め） | ウェイト 300–400、大文字、字間 0.3em 前後。キッカー・セクション番号・小さな注記にだけ使う |

- 見出しは明朝、本文はゴシック、という「編集の基本形」を崩さない。
- フォントサイズは階層を少なく保つ（本文 13–15px、見出しは clamp で可変）。
- 丸ゴシック体は使わない（甘さ・AIっぽさの温床になるため）。

## 3. 色の使い方

| 名前 | 値 | 用途 |
|---|---|---|
| 生成り（paper） | `#f7f3ec` | 地色の基本 |
| 生成り・濃（paper-2） | `#efe9dd` | ホバーや面の切り替えの最小限の差 |
| 墨（ink） | `#26221c` | 文字・罫線・ボタンの主色 |
| 墨・淡（ink-soft） | `#6f695c` | 本文の補助、説明文 |
| 罫線（line） | `#d8d1bf` | 1px の区切り |
| 苔（accent） | `#4c5844` | 抑制したテーマ色。キッカー、番号、小さなラベルにだけ、面では使わない |

- 色は「生成り・墨・罫線」が 9 割。アクセントは点で使う。
- テーマ壁紙そのものが色の主役。UI 側の色は絵を引き立てるために黙る。
- グラデーションは原則使わない（特にピンク系は禁止。下記「禁止事項」参照）。

## 4. 余白と罫線の原則

- 区切りは影ではなく **1px の罫線** で作る。ドロップシャドウは使わない。
- 余白は大きく取る。セクション間は 100px 級、見出しと本文の間も詰めない。
- 角丸は最小限（0–6px 程度）。ピル型（999px）のボタン・バッジは使わない。
- 要素は「面で囲う」より「線で区切る」。カード化しすぎない。
- 雑誌の特集ページの構成を手本にする：大きな明朝の見出し、小さな英字キッカー、番号付きセクション（No.01 — …）、キャプション付きの図版。

## 5. 禁止事項（AIっぽい要素のリスト）

以下は「AIが作ったっぽさ」の正体として、今後も新規デザインに持ち込まない。

- ピンク系（に限らず安易な）グラデーション背景・ボタン
- 絵文字の装飾的使用（🎀、⚠️、✨ など）。記号も最小限にする
- 過剰な角丸（大きな radius、ピルボタン、ピルバッジ）
- ドロップシャドウで浮かせる表現の多用
- 丸ゴシック体、太字だらけの見出し
- 「バッジ＋グラデーション＋影付きカード」の量産型ヒーロー構成
- 色の数を増やしてごまかすこと。迷ったら色を減らす
- 意味のないアイコン円形背景、ホバーで跳ねる・浮く演出の乱用

## 6. 画風の方向性（テーマイラスト）

- 参考は出水ぽすかの絵作り。ただしよりシンプルかつクリアに、引き算を大事にする。
- 細い線、色数は抑制、余白多め。9 テーマで画風を統一する（詳細は THEME_SPEC.md）。
- テーマごとに世界は違っても、「静けさ」の温度感は揃える。
- 新テーマ追加時も、この温度感と線の質を審査基準にする。

## 7. 使いやすさの原則

- 美しさと使いやすさは両立させる。判断は常にユーザー目線。
- ダウンロード導線は常にページ上部から迷わず辿れること。OS ごとの違いは一言で添える。
- 初回起動の確認画面など「つまずきポイント」は、隠さず先回りして案内する。
- ユーザーの声（GitHub Issues / Discussions）を分析し、嬉しいと感じる機能・困っている点を次の改善に反映する。

## 8. 改善の積み重ね方

- 週次レビューで、サイト／アプリのデザイン改善を必ず 1 件実施し、ここへ学びを追記する。
- 大きな方向転換をするときは、この文書の該当節を先に更新してから実装する。
- 「何を変えたか・なぜ変えたか」を残す。ブランドは記録の蓄積で育つ。
