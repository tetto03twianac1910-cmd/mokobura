# もこブラ 集客戦略メモ — 2026年内に利用者1,000人

作成: 2026-11-21 / 対象期間: 2026-11-21 〜 2026-12-31（約6週間）

## ゴールと前提

- **ゴール**: 2026年12月31日までに利用者1,000人。
- **「利用者」の数え方**: まず GitHub Releases のダウンロード総数を主指標にする（サーバーなし設計のため、アプリ側の計測は入れていない）。スター数・公式サイト流入は補助指標。
- **現状**: v0.1.0 を公開した直後。署名なし・開発中であることは隠さず、誠実さ自体を信頼の材料にする。
- **制約**: 広告費はかけない（オーガニックのみ）。運用はほぼ自動化が方針なので、施策は「資産として残るもの」（記事・動画・リポジトリ整備）を優先する。

## 数字の置き方（目安）

1,000 DL を6週間で割ると週あたり約170 DL。1チャネルで届く数字ではないので、複数チャネルの積み上げで考える。

| 柱 | 狙う寄与 | 根拠 |
|---|---|---|
| 記事（Zenn/Qiita/note） | 300〜400 | 検索とシェアで長く効く。技術層＋かわいいもの好き層の両方に届く |
| X（テーマ画像の投稿） | 200〜300 | 画像が拡散しやすい領域。テーマ追加のたびに投稿できる |
| GitHub 内（検索/topics/スター） | 100〜200 | topics 整備済み。README の見栄えとスターの蓄積でじわじわ増える |
| ショート動画（YouTube/TikTok） | 100〜200 | 着せ替えの「変わる瞬間」は動画向き |
| 海外（Product Hunt / Reddit） | 100〜 | kawaii 文化への関心層に一発を狙う |

※あくまで配分の目安。週次で実績を見て配分を寄せ替える。

## チャネル別アクション

### 1. GitHub（土台・常時）
- [x] topics 設定（browser, electron, kawaii, theme, customization, japanese, cute, chromium）
- [x] README を公開向けに整備（キャッチ、公式サイト・DLリンク、テーマ画像、フィードバック募集）
- [x] homepage に公式サイトを設定
- [ ] Social preview 画像を設定（テーマ画像のコラージュ。GitHub の Settings → Social preview は手動のみ）
- [ ] リリースごとにリリースノートを日本語＋英語で書く（検索に引っかかる）
- [ ] Issues に「感想・要望」用の導線を README とサイトに明記済み → 来た声には必ず返信する（最初の10件が特に大事）

### 2. X（週2〜3回）
- テーマ画像1枚＋短文の投稿を基本形にする（下書きは `posts.md`）。
- テーマ紹介を9回シリーズ化できる（1テーマ1投稿）。着せ替え前後の比較画像も効く。
- ハッシュタグは盛りすぎず2〜3個まで（例: #個人開発 #かわいい）。
- リリース・テーマ追加など「出来事」がある日に合わせて投稿する。

### 3. 記事（Zenn / Qiita / note）
- Zenn か Qiita に技術寄りの開発記事を1本（構成案は `posts.md`）。「Electronで着せ替えブラウザを作った」切り口。
- note には非技術層向けの紹介文（世界観と使い方中心）。
- 記事末尾には必ず公式サイトと GitHub へのリンクを置く。
- 反応が良かった記事は続編（テーマ追加報告、ユーザーの声への対応報告）に繋げる。

### 4. ショート動画（YouTube Shorts / TikTok）
- 15〜30秒:「ブラウザを着せ替えたらこうなった」テーマ切替の録画。
- 9テーマ分＋比較動画で本数を稼げる。週1本ペースでも6本。
- 概要欄に公式サイトリンク。コメントには必ず返す。

### 5. 海外（Product Hunt / Reddit）
- Product Hunt は英語ページとスクリーンショットを整えてから1回投入。ローンチ日を決めて X と連動させる。
- Reddit は r/kawaii、r/browsers、r/opensource あたり。宣伝色を抑え、「作ったので感想がほしい」形式で。サブレディットのルールを必ず確認してから投稿する。
- README に英語の一文要約を足すと海外からの理解が早い（今後の改善候補）。

### 6. テーマ追加＝発信イベント
- テーマを1つ追加するたびに、X投稿・リリースノート・（可能なら）動画をセットで出す。
- 「次のテーマのリクエスト募集」を Issues や X で行うと、参加感が生まれて再訪理由になる。
- 季節テーマ（年末・年始など）は時期に合わせて先行告知する。

## 計測と週次振り返り

毎週1回、同じ曜日に数字を記録してこのファイルか別表に追記する。

| 指標 | 取得方法 |
|---|---|
| DL総数・リリース別DL | GitHub API: `repos/:owner/:repo/releases` の `assets[].download_count` |
| スター数 / フォーク数 | リポジトリ画面 or API |
| 公式サイト流入 | GitHub Pages は標準では解析なし。当面は流入元が分かる指標（記事のいいね、Xのインプレッション）で代替。必要になったら無料のアクセス解析を検討 |
| Issues・感想の件数と内容 | Issues 一覧。内容は「テーマ要望 / 不具合 / 感想」に分類 |

振り返りで見ること:
- どのチャネル経由の伸びが大きかったか（DLの増分と投稿・公開のタイミングを突き合わせる）
- 来た声の中で「次に直す・足すもの」を1つ決める
- 翌週の発信ネタ（テーマ追加、改善報告、記事）を1〜2個決める

## リスクと正直な注意点

- 署名なしアプリは初回起動のハードルが高く、DLしても起動しない人が一定数いる。案内文（サイト・README）で手順を明示して取りこぼしを減らす。
- 1,000人は意欲的な目標。届かなくても「どのチャネルが効いたか」のデータが残れば次の期間に活きる。数字は盛らない。
- 宣伝のしすぎは逆効果。各コミュニティのルールと空気を尊重し、宣伝より「作ったものを見せる・声に応える」を基本にする。
